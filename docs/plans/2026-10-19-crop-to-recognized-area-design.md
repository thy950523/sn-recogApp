## 1. 背景

识别结果页现在显示的是**整张拍摄载荷**（最长边 ≤1600px，`ScanView.encodePayload`）。
实测的问题：用户拍一张「标签偏在一侧、周边大片桌面」的照片时，标签在 343px 宽的列里
只渲染出约 150px —— 屏幕的大半被无关环境占着，候选列表还被挤到下面。

目标：按 OCR 实际识别到的框裁剪，只留框的包围盒 + 四周约 50px 留白，
把无关区域裁掉、让标签真正变大。

---

## 2. 关键决策

| 决策点 | 结论 | 理由 |
|---|---|---|
| 裁剪依据哪些框 | **全部候选**的 `snBox` + `barcodeBoxes` | 稳定：展开/收起疑似候选区时图不会跳动，且任何框都不会落到裁剪区之外。代价是远处幽灵候选会把包围盒撑大（退化成「几乎没裁」），但那只是不生效，不会出错 |
| 50px 的坐标系 | **原图像素** | 载荷最长边 ≤1600px，50px ≈ 图宽 3%；对应屏幕上约 11px 留白。padding 的职责只是「不切到标签边缘」，不需要更多 |
| 裁剪作用域 | **只影响识别结果页的展示** | IndexedDB 里存的仍是拍摄原图、Excel 导出的原图页也仍是原图（上一版刚改成「不再二次编码」）。照片作为留证的价值不变 |
| 看整图的入口 | **点图在「特写/整图」间切换** | 裁剪会把「OCR 完全没识别到的设备」一起裁掉（它没有框）。没有入口的话，用户看不到「画面里其实还有一台」，只能靠重拍撞运气 |
| 裁法 | **真裁（canvas → 新 dataUrl）** | 见 §3。CSS 视口裁剪做不到「标签变大」，除非测量渲染尺寸 |
| 裁剪时机 | 识别**完成后**才算，识别中显示整图 | 识别本身需要整图来找框；整图 + 转圈也是「正在处理你拍的这张」的反馈 |
| 裁剪是否随 UI 变 | **只算一次**，来源是 `result.devices` 而非 `rows` | 删行、改 SN、展开疑似区都不该让图跳动 |
| `max-h-[40dvh]` | 不动 | 竖构图下它才是真正的约束（1600×2133 在 343px 列里渲染成 200×267）。裁剪的放大倍数因此有上界，但同一块 40dvh 里装的从「周边环境」换成了「标签本身」——这正是要的效果 |

---

## 3. 为什么是真裁而不是 CSS 视口裁剪

**CSS 视口裁剪**（保留原 dataUrl，`overflow:hidden` 容器 + 图片负偏移只露出裁剪区）
零编码、零画质损失，但它要么做不到「标签变大」，要么得靠测量：

要让标签变大，必须让 `<img>` 的渲染宽度**大于**容器（`width: 100/cropW %`），
而容器尺寸又得独立于 `<img>` —— 容器宽 = 列宽、高按裁剪比、还要被 `max-h-[40dvh]` 封顶。
`aspect-ratio` + `max-h` 组合下，块级元素的宽度是 stretch 的、**不会随被夹紧的高度回缩**，
比例会破（图被压扁或裁少一条）。绕开就得测量渲染尺寸（ResizeObserver），把简单问题做复杂。
若不放大，裁剪就只是「去掉周边」，标签在屏幕上一点没变大 —— 没达成目标。

**真裁**：按包围盒 + 50px 在原图像素上裁一块画进新 canvas，`toDataURL('image/jpeg', 0.92)`。
展示层代码几乎不动（还是那个 `<img className="max-h-[40dvh] max-w-full">`），
标注层只需把归一化坐标做一次仿射映射。代价是一次 JPEG 编码 —— 但只编码裁剪区
（比整图小得多），且发生在识别完成、结果即将出现的那一帧，不是拍照卡顿那条路径。

## 4. 实现

### 4.1 新增 `src/lib/cropImage.ts`

几何全做成纯函数，只有最后一步碰 canvas：

| 函数 | 职责 |
|---|---|
| `CROP_PADDING_PX = 50` | 四边留白（原图像素） |
| `collectBoxes(devices): Box4[]` | 全部候选的 `snBox` + `barcodeBoxes`，跳过 null |
| `cropRectForBoxes(boxes, imgW, imgH, padPx): PixelRect \| null` | 包围盒 → 像素矩形，四边各加 pad，clamp 到图内，取整；无框、或裁剪面积 ≥ 整图 95% 时返回 null |
| `remapBox(box, rect, imgW, imgH): Box4` | 归一化框 → 裁剪坐标系（仍是 0~1） |
| `cropImagePayload(img, rect): ImagePayload \| null` | 建 canvas、`drawImage` 九参数版、`toDataURL`；失败返回 null |

「面积 ≥95% 短路」是一行判断，省掉一次无意义的编码，也避免
「点下去什么都没发生、却卡了一下」。

### 4.2 `src/sections/MultiResultView.tsx`

- effect 里的 promise 由 `Promise<MultiRecognizeResult>` 改为
  `Promise<{ result; cropped }>`：结果落地后**在同一个作用域内**算裁剪图，
  `img` 还在手上，不必再解码一次。`inflightRef` 的按 dataUrl 去重语义不变。
- 新增 state：`cropped: { image: ImagePayload; rect: PixelRect } | null`（结果落地时设一次）、
  `showFull: boolean`（默认 false）。
- 展示的图 = `showFull || !cropped ? image : cropped.image`。
- 标注层加一层 `mapBox`：显示裁剪图时 `remapBox(...)`，否则原样返回；
  `boxStyle` / `badgeStyle` 不动。
- 图片容器加 `onClick` 切换 `showFull`，右上角放一个「特写 / 整图」小角标 ——
  纯点图没有任何可见提示，用户发现不了。`cropped` 为 null 时不显示角标、点击为空操作。
  标注层是 `pointer-events-none`，点击会正常落到容器上。

### 4.3 不改的部分

`imageStore`、`exportExcel`、`RecordsView`、`registerRows`、`multiRecognize` 全部不动。
（记录页本来就不显示照片，全项目只有 `MultiResultView` 一处 `<img>`。）

## 5. 边界情况

| 情况 | 行为 |
|---|---|
| 没有任何框（未识别到 / 降级模式 / 用户删光行） | 不裁。**降级模式自动不裁是白捡的**：`markUnverified` 已把锚点候选的 `snBox`/`barcodeBoxes` 清空（合成坐标不可信），`collectBoxes` 自然拿不到框，不需要额外开关 |
| 框贴边 | clamp 后不越界，那一侧 padding 自然小于 50px |
| 裁剪区极小（只识别到一个 30px 条码框 → 130×130） | `max-w-full`/`max-h` **只缩不放**，按原尺寸渲染，不会糊。不需要最小尺寸保护 |
| 裁剪区几乎等于整图（远处幽灵候选撑大包围盒） | 返回 null（§4.1 的 95% 短路），退回整图 |
| 极端宽高比（一行标签贴满图宽） | 裁成全景条，`max-h` 不再是约束，图很矮 —— 正好给列表让位 |
| `toDataURL` 抛错或返回 `data:,` | 返回 null，退回整图 + `console.warn`。**不弹错误**：裁剪是锦上添花，不该打断登记流程 |

**失败通路**：裁剪失败不改变任何既有行为 —— 落盘、`imageSaving`、`imageSaveFailed`、
登记流程一概不碰。这一版不新增任何用户可见的错误通路，只新增一个控件（角标）。

## 6. 测试

纯函数用 vitest 覆盖：

- `collectBoxes`：空 devices → `[]`；snBox + 多条码框 → 全收；
  `snBox` 为 null 的仅条码候选只收条码框。
- `cropRectForBoxes`：单框居中 → 四边各 50；框贴左上 → clamp 到 0、不出现负值；
  多框 → 包围盒；空数组 → null；面积 ≥95% → null；输出为整数。
- `remapBox`：裁剪区内/外的框映射后的坐标、相对顺序与包含关系不变。
  **「裁剪区外的框映射后落在 0~1 之外」要显式断言** —— `remapBox` 不该假装这种情况不存在。
- **不测** `cropImagePayload`（需要真 canvas），与仓库现状一致（canvas 代码都不测）。

## 7. 验证

- `npx vitest run` 全绿（**基线 8 文件 / 180 用例**，已实测）。
- `npx tsc -b` 通过（**不是** `tsc --noEmit`，那在本仓库是空操作）。
- 手工：
  1. 拍一张标签偏一侧、周边大片桌面的照片 → 确认结果页裁到标签附近、框仍对齐；
  2. 点图切整图 → 框跟着重新对齐；
  3. 关掉 OCR 服务走降级路径 → 确认不裁、不报错、无角标。

## 8. 已知取舍

- **放大倍数有上界**：受 `max-h-[40dvh]` 约束，竖构图下裁剪不会让标签无限变大。
  想更激进得调这个值，但那是「列表让多少空间给图」的另一个决定。
- **远处幽灵候选会让裁剪退化成不生效**：这是「稳定优先」的代价（见 §2 第一条）。
  它不会出错，只是没效果。
- **裁剪图是第二代 JPEG（0.92）**：只用于屏幕展示；入库与导出的仍是原图字节，
  不受影响。
- **疑似候选的框在裁剪区外的情况**：按「全部候选」取包围盒后，正常路径下不会发生；
  但 `remapBox` 不对此设防，超出 0~1 的框会照实映射出去（由测试锁住这个行为）。
